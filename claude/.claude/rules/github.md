# GitHub(Issue・PR・レビュー)

## Issue と PR の紐付け
- `Resolves #xxx` はサブタスクを持たない末端 Issue にだけ付ける。親がいても末端なら付けてよい
- サブタスクを持つ Issue(親・中間)は本文で `- #xxx` と番号参照するだけにする。サブタスクの有無は `gh api graphql` で確認する
- 親 Issue を直接クローズしない。サブタスク単位でコメント・クローズする
- `not_planned` は対応しないと確定したときだけ使う。情報待ちや今後対応予定のものは open のままにする
- PR を作る前に、リポジトリの PR テンプレートを探して従う

## 他人の PR をレビューするとき
- 要約を返すだけで終わらせず、GitHub のインラインコメントで該当行に投稿する(pending review → コメント追加 → submit)
- 指摘には Must / Should / Nit を付ける。Must が1件でもあれば request changes、それ以外は approve か comment
- 自分の PR のセルフレビューは GitHub に投稿せず、チャットで報告して必要な修正だけ反映する

## 自分の PR への指摘に対応するとき
- 指摘の前提を、実際のコード・依存先のソース・公式ドキュメントで確認してから対応する
- 前提が誤っている指摘には、根拠(コミット SHA、出典)を示して丁寧に反論する
- 本物のバグは再現してから直し、回帰テストを付ける
- 挙動・セキュリティに関わる判断や、業務知識が必要な判断は、独断せずユーザーに確認する
- 返信は PR 本文の更新ではなく、各スレッドへのコメントで行う
