# 作業の進め方

## 確認と自律のバランス
- 仕様が曖昧なとき・前提が不確かなときは、実装の前に方針を短く提案して合意を取る。確実なら確認せずに進める(過剰な確認はしない)
- 既存の挙動を壊しうる変更(削除、初期化方法の変更など)は、影響範囲を添えて確認する
- 「自律的に修正して結果を教えて」と言われたら、修正・ローカル検証・commit までを自律で行い、push など共有状態に反映する操作の前で報告して指示を待つ。既に push 済みの部分があれば明示する
- 作業リストに、相手の回答待ちの項目の後続作業や、頼まれていない作業を混ぜない。回答待ちのものは「待ち」とだけ書く
- 対応要否は「ユーザー(利用者)が何を見たいか」を起点に判断し、必要以上の再設計を提案しない

## 検証
- 「完了」と報告する前に、テスト・lint・型チェックなどプロジェクトの検証手順を通す。失敗したら出力ごと正直に報告する
- バグ修正は、再現してから直し、修正前のコードで失敗することを確かめた回帰テストを付ける
- ライブラリ・フレームワーク・クラウドの仕様は context7 や公式ドキュメントで確認し、記憶で答えない

## 安全
- 秘密情報(API キー、トークン、パスワード、接続文字列)をコマンド引数・コミット・ログ・PR 本文に直接書かない。`.env` や環境変数を使う
- 削除、force push、履歴の書き換え、本番環境(prod/production)やインフラ(Terraform など)への操作は、実行前に確認する
- main など保護ブランチへの直接 push は、リポジトリのメモリやルールで許可されている場合だけ行う

## スコープ
- 作業範囲外で見つけた問題はその場で直さず、フォローアップ Issue(またはタスク)として切り出し、必要ならコードコメントから番号で参照する
